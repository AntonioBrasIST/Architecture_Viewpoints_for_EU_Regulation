# AI Skill Specification: viewpoint-materializer

## 1. Semantic Metadata
* **Skill Identifier:** `viewpoint-materializer`
* **Short Summary:** Translates a pre-defined viewpoint scoping document into a rigorous ArchiMate viewpoint definition, specifying the exact metamodel concepts, relationships, and representation rules required.
* **LLM Routing Description:**
  > "Use this tool to convert a scoped viewpoint boundary (typically produced by the viewpoint-scope-definer) into a concrete, executable ArchiMate Viewpoint specification. The tool requires a scoping document detailing operational and legislative boundaries. Do NOT use this tool if the scope and boundaries have not yet been defined. Do NOT use this tool to draw actual diagrams."

## 3. Core Logic & Execution Flow

### A. Theoretical Foundation (Viewpoint Materialization)

When executing this skill, the AI acts as an **Enterprise Architecture Methodologist**. It takes the conceptual boundaries (the "what and why") and translates them into the strict syntactic and semantic rules of the ArchiMate language (the "how"). It defines the exact lens through which the architecture will be viewed to answer the concerns highlighted in the scoping document.

### B. Execution Step-by-Step

1. **Ingest Scope:** Read the scoping document, approved Coverage and Relationship
   Ledgers, and contextualized immutable overview baseline. Preserve its legal core
   and approved stakeholder/legal-role chain in View 0.
2. **Pre-Execution Validation:** Ensure the scoping document explicitly contains boundaries, inclusions, and a legislative focus. If any of these are missing, **HALT** and ask the user to clarify or provide a complete scoping document.
3. **Parameter Deduction & Perspective Disambiguation:**
* **Stakeholders & Purpose:** Deduce who consumes this view based on the scope, and categorize the purpose strictly as *Informing*, *Deciding*, or *Designing*.
* **Concerns & Perspective Classification:** Translate the "Legislative Focus" and "Scope Justification" into clear, actionable architectural concerns, explicitly categorizing each concern under one of three universal architectural perspectives:
  - **`[Governance]`:** Policy frameworks, executive/board oversight, regulatory accountability, and risk appetites.
  - **`[Administrative]`:** Procedural workflows, change request authorizations, approval sign-off gates, segregation of duties, access request approvals, and documentation management.
  - **`[Technical]`:** Execution-level tools, automated and manual quality/security verification mechanisms (unit testing, SAST scans, SCA dependency checks, performance tests, code reviews), runtime telemetry, and infrastructure deployment controls.
* **Concepts (Metamodel Mapping & Requirement-Family Hierarchy):**
  - **Requirement-Family Representation:**
    - Model each coherent control domain as a meaningful parent `archimate:Requirement` or `archimate:Constraint`, never as an Article, annex, legal heading, or `Grouping` element.
    - Model every scoped granular statutory requirement, restriction, or obligation as a distinct target-qualified child `archimate:Requirement` or `archimate:Constraint`. Keep its binding Article citation and approved direct legal-text IDs in documentation or ledger metadata, not as a visible source node. Parent families carry only their ordered, deduplicated child roll-up. IDs must not appear in titles, visible labels, or slide diagrams.
  - **Operational Footprint Representation:** Translate the operational inclusions into official ArchiMate elements based on their perspective domain (e.g. *Business Process / Sign-off* for Administrative, *Application Component / Test Artifact / Automated Pipeline* for Technical).
  - **RULE OF DOMAIN COHESION:** Ensure concepts addressing the same functional domain (e.g. all technical software testing and verification controls) are mapped into cohesive model element groups rather than split across unrelated views.
* **Relations (Requirement-Family Realization Hierarchy):**
  - **Family $\rightarrow$ Child Decomposition:** Use `archimate:CompositionRelationship` to connect each meaningful parent family to its specific child requirements. The composition is semantic; visual containment represents it without an internal canvas arrow.
  - **Operational Footprint $\rightarrow$ Requirement Realization:** Use `archimate:RealizationRelationship` to model how operational processes, application components, or artifacts realize statutory requirements (e.g., `PR Review Process` $\xrightarrow{\text{realizes}}$ `REQ-Art9-PeerReview`).
  - **Ownership-Safe Relations:** Create realization only for `Directly performed` coverage. For `Stakeholder-constrained`, represent the stated approval or dependency; for `Externally owned`, represent the known external role/process; for `Not evidenced / unclear owner`, retain the status in documentation without inventing a responsible element.
  - **Operational Gap Mapping:** For unperformed or missing requirements, model them as unrealized requirements associated with an `archimate:Assessment` (friction) or `archimate:Gap` via `archimate:AssociationRelationship`.
  - **Operational Inter-Layer Relations:** Connect operational elements using official ArchiMate relationships (e.g., *Serving*, *Assignment*, *Access*, *Triggering*, *Flow*).


4. **Complete relationship presentation:** Apply `regulatory-view-structure` and
   materialize every approved `REL-*` edge. Do not restrict links to selected
   categories or a density-safe subset. Composition/Aggregation may be
   semantic-only only when matching nesting communicates it.
5. **Graph artifact and validation:** Emit `7_view_graph.json` with schema version
   `1.0`, stakeholder anchor, root warning threshold 30, node/relationship catalogs,
   evidence/approval fields, and exact per-view membership. Invoke
   `connected-view-validator` and `Methodology/tools/view_graph_validator.py`.
6. **Additional Information:** Define visual cues and nesting rules. Internal composition lines are suppressed only when a child is visually nested under its parent.
7. **Output Generation:** Format the Markdown viewpoint and JSON graph contract.

## 4. Safety, Boundaries & Error Interception

* **Zero Assumption Rule:** The LLM must derive the viewpoint parameters *only* from the provided `scoping_document`. If the operational context is too vague to assign a specific ArchiMate concept, the LLM must **HALT** and ask the user for clarification.
* **Strict Title Purity & Length Guardrail (MANDATORY):**
  - **Maximum Length:** Every element name across all catalogs MUST be $\le 25$ characters.
  - **Zero Notation Symbols in Titles:** Element names must NOT contain bracketed notation strings such as `[Person]`, `[badge]`, `[Right Arrow]`, `[UML Box]`, `[Folded Page]`, `[3D Cube]`, `[Pill]`, `[Ball]`, etc.
  - **Tag-Only Gap Representation:** Never put `[Gap]` or disclaimer sentences (e.g., `- potential visibility limit...`) into the element name. An element representing a gap is typed as `archimate:Gap` and tagged via metadata or notes, with its clean name representing the missing capability (e.g., `Crash Test Absence`, `BCP Drill Absence`).
* **Interactive Validation Gates:** Before saving, first present the whitelisted ArchiMate concepts, relations, and visual rules:
  * **Header:** `Confirm Metamodel Scope`
  * **Question:** `"I have materialized the viewpoint specification. Here is the proposed metamodel scope: Target Stakeholders: [Stakeholders], Allowed Concepts: [Allowed Concepts], Allowed Relations: [Allowed Relations], Visual Rules: [Visual Rules]. Do you agree with this formal metamodel and viewpoint specification?"`
  * **Options:** `Yes (Recommended)`, `No` (with custom feedback)
  * **Gate 7.2 Header:** `Confirm View Graph`
  * **Gate 7.2 Question:** Present every view's textual relationships, stakeholder
    path, component result, and root warning. Ask the operator to approve the exact
    `7_view_graph.json` content.
  * **Execution Rule:** Save neither `7_viewpoint.md` nor `7_view_graph.json` until both gates pass.
* **Strict Metamodel Compliance:** The LLM must only output standard, official ArchiMate concepts and relationships. It must not invent custom element types (e.g., it cannot output "Regulation Element"; it must use *Meaning*, *Requirement*, or *Constraint*).
* **Scope Creep Prevention:** The materialized viewpoint must not expand beyond the boundary explicitly defined in the input document.
* **Coverage Completeness:** Reject materialization if an approved coverage entry lacks thematic-view membership, or if a non-direct ownership state is presented as stakeholder realization.
* **Legal-anchor completeness:** Reject materialization if a legal Requirement/Constraint lacks direct IDs (child) or a correctly ordered, deduplicated child roll-up (parent). Generators serialize these IDs into documentation only.
